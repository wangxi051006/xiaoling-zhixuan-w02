# 校零智选 · 后端架构设计

**v1.0｜2026-11-18｜实施基准** · [实现拓扑](./2026-11-18-backend-topology.svg) · [实施总计划](../plans/2026-11-18-backend/00-master.md)

本版替代上一版微信首发/仅即时配送的提案。已确认：**单校单站、即时与预约配送、货到付款或余额支付、微信支付显示待接入、Go 首发、Rust 有数据再接入**。余额是否上线单独过门禁，关闭余额不影响货到付款。下文的运营参数为试点默认值，不是对外 SLA。

## 1. 以现有三端为准

[项目入口](../../../index.html) 选定「03 手账」，[交互演示](../../../demo/index.html) 与 [app.js](../../../demo/app.js) 用共享浏览器内存模拟订单、配送和退款，不接入真实业务。原型结算中的固定预约选项替换成服务端时段，微信支付选项改为只读「待接入」。保留 [用户端](../../../demo/ui-user.js) 的购物袋、楼栋地址、结算和订单时间轴；保留 [配送端](../../../demo/ui-delivery.js) 的上线、抢单、取货、送达和收入明细；保留 [管理端](../../../demo/ui-admin.js) 的商品、库存、订单、放单、骑手和看板，补充预约配置、收款对账及异常处理。生产不发布切换角色、重置、自动造单、假营业额、提现、积分券、定位、评价、自提或写死 ETA；无相应数据时显示空态。延期功能不是首发验收项。

## 2. 运行拓扑

- **一个 Go 模块化单体**：`net/http`、`pgx`、显式 SQL、版本化迁移、REST/OpenAPI。站点、库存、订单、资金、配送在一个 PostgreSQL 内协作。同进程后台处理预约提醒、任务租约与异常提醒，入库去重并可重跑，不依赖 Redis、消息代理或 WebSocket。一台 Linux 应用主机是单点，首版不承诺高可用。
- **静态前端**：Vue + TypeScript + Vite，沿用自绘 CSS/SVG，三个独立构建入口/同源 API；保留原型作视觉对照，不部署 `demo/`。用户与骑手独立公网域名，管理入口通过 VPN/访问网关；Caddy 处理 HTTPS、静态资源和反代，Go 监听回环，托管 PostgreSQL 走私网；监控、审计副本走独立受限存储。没有微信 SDK、支付密钥、商户配置或回调路由。
- **身份**：用户默认手机号 OTP（服务端调用短信供应商，部署前确认可用性）；骑手和管理员经员工 OIDC + MFA，角色和站点由应用绑定；不是同一套登录凭据。真实短信与 IdP 均不可用时，不开公网试点，dev/test 假服务不得进生产。Cookie 限本域、`Secure`、`HttpOnly`、`SameSite=Lax`，写请求还检查 CSRF/来源，停用账号撤销会话。
- **Rust 边界**：Go profiling 与端到端压测证明确有 CPU 瓶颈且独立交付有收益，再考虑异步批处理等场景；不做 FFI、不复制交易算法、不直接写核心交易表。

## 3. 预约与即时共用同一容量池

采用站点显式生成的 15 分钟交付窗口，试点预约最多 3 天，提前量默认 15 分钟（`dispatch_at = start_at - lead_time`）；均可配置，禁止编辑已占用窗口的时间与计数口径。站点时区 `Asia/Shanghai`，数据库以 UTC `timestamptz` 保存，营业区间和跨日按站点本地时间解释，窗口为 `[start_at, end_at)`。服务端时钟为准。

- `SCHEDULED` 明确提交 `slot_id`；只有 `now < dispatch_at` 且窗口在预约范围内可下单。`ASAP` 由服务器选最早有容量且离结束至少 10 分钟的营业窗口；下单沿用报价的窗口，若满或过期则明确重新报价，不静默换档。报价不占位，提交原子占一个窗口名额并预占库存。没有窗口则拒单；不为超额订单捏造 ETA。默认一单占一份容量。
- 预约创建为 `SCHEDULED`，到 `dispatch_at` 由后台幂等转 `PREPARING`，运营可看待备货队列；即时创建直接进入 `PREPARING`。窗口开放任务前由管理端确认备货完成；只有备货已完成且订单可履约才能放单。晚于窗口末仍未完成标记逾期并告警，不能静默换档/取消/送达。
- 窗口容量计数是接单预算，不是活跃任务数；未分拣且在窗口结束前取消可释放容量，其他情况保留计数，不因送达或退回而重复出名额。商品在下单时预占到取货/取消；只锁实际需要的基础单位，三件装消耗 3 个。取货同时扣减实存和预占；已分拣取消经运营归架确认才释放库存，损坏走调整；已取货退回必须验收入库，不随退款自动回库。

## 4. 订单、结算和履约

金额是整数分，折扣是整数基点，服务端按 SKU 选最高满足阶梯且不叠加，单件舍入到分后乘数量。快照保留金额、规格、交付窗口、必要地址与联系人。**下单事务**：身份/归属与幂等 → 重校报价、窗口、货到付款额度与库存 → 预占 → 写订单与结算记录 → 若 `BALANCE` 同事务扣余额并落不可变流水 → 写事件与后台任务。任一步失败全回滚。已存在同账号/操作/幂等键且参数相同则返回原结果，异参拒绝；前端不上传权威金额、收款人角色或状态。

| 方式 | 行为与拒绝条件 |
| --- | --- |
| `COD` 货到付款 | 首发可独立启用。下单资金 `COD_UNCOLLECTED`，骑手交接时确认**已实际收到全款现金**，只能由当前指派骑手操作；已收款与送达在同一个事务，收款、配送收入各一条，拒付/少付不允许按已收完成，进入退回异常流程。骑手上缴由财务复点对账，骑手不能标已上缴。未收款取消无退款。已收款全退须运营发起、财务审核并记录线下实际退款凭据；不伪造原路退款。试点每用户最多一笔活跃 COD，按账号与来源限频，防止无成本占位。 |
| `BALANCE` 余额支付 | 完整实现、生产默认关闭。通过核准来源建立余额，普通用户及普通管理员均不可充值、改余额或自行发放；没有充值/提现/转账/组合支付。钱包锁定、禁止负数、账本追加、扣款及退回原钱包有唯一业务键。自助取消触发固定规则退回；人工全额退款经两角色审批。余额不足不自动切 COD，关闭新余额支付不影响已有余额单退款。真实余额来源、使用规则、账本/初始总额对账及适用合规未获批准时只验收测试余额，不启用生产开关。 |
| `WECHAT` 微信支付 | UI 禁用并标「待接入」，直接请求得到 `PAYMENT_METHOD_DISABLED`；首发不存在支付、退款、通知或客服模拟成功接口。 |

**履约路径：** `SCHEDULED`（仅预约）→ `PREPARING` → `READY_FOR_CLAIM` → `AWAITING_PICKUP` → `IN_DELIVERY` → `DELIVERED`。未放单的本人订单可自助取消（预约取截止前；即时仅未分拣的 `PREPARING`）；其他未取货取消/回收由运营处理并留痕，取消为 `CANCELED`。取货后拒付或异常 `RETURNING` → `RETURNED`，运营验收退回后才可回库，不计默认配送报酬。已送达后的退款不抹掉履约历史。资金状态、COD 上缴状态、履约状态分别记录。大厅只露出楼栋/区域、件数、费用和时间窗；任务归属唯一，每骑手至多一笔活跃任务；双抢返回 `409`。大厅前台 10 秒轮询，抖动/退避，历史脱敏。

未送达且运营确认退回后，同一事务结束履约、按验收回库、退原钱包或撤销未收 COD；失败时回退整笔变更。已送达才走人工售后退款审批，退款与取消共用订单级唯一约束。

## 5. 运行与安全基线

预发/生产独立密钥、账号、网络、数据库；生产非 root；应用、迁移、备份角色分别授权；Caddy 关闭不需要的入口，诊断和数据库不公开；CSP、参数化 SQL、固定请求体与列表上限、输出默认转义；OTP/下单/催单限频。记录请求 ID、操作对象和原因，不写完整电话/房间、OTP、令牌或账本凭据原文。审计独立追加与转存，复核管理退款、COD 差异、库存修正和余额批次。

独立安全审计由非实现者复核，参考 ASVS L2；证据、阻断项与签署见 [验收计划](../plans/2026-11-18-backend/08-acceptance.md)。开真实余额前运营/财务须独立复核其来源与适用义务，本设计不对具体主体作合规判断。启用备份与 PITR；隔离环境实际演练恢复、资金/库存对账再恢复写入。试点目标：RPO ≤ 15 分钟、RTO ≤ 2 小时；持续 15 分钟、50 个并发用户 + 20 个骑手轮询，列表 P95 ≤ 200ms、下单本地事务 P95 ≤ 500ms、HTTP 5xx < 0.5%，且无超卖、超预约、双扣或重复收入；须实测。
