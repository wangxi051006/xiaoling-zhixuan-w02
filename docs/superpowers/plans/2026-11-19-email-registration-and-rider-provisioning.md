**目标：** 普通用户可用邮箱验证码自助注册和登录；骑手只能由授权管理员从后台开户；平台用专用发件地址发送验证码和事务通知。

**技术与边界：** 沿用 Go、PostgreSQL、Vue/TypeScript、OpenAPI 生成链、员工 OIDC/MFA 和「03 手账」。保留手机号登录和收货联系方式。仅使用合成数据与授权测试资源。不部署生产，不改支付模式或既有放行状态。

## 1. 账号迁移与兼容

- [ ] 先补带有老客户、员工和历史订单的升级回归。检查 `backend/internal/identity/` 中 `phone IS NULL`、`phone IS NOT NULL` 等角色判定及相关查询，替换为明确的客户/员工类型。客户支持已验证手机号或邮箱；员工继续按受信 IdP 的 `issuer/subject` 识别。

## 2. 用户邮箱注册与登录

- [ ] 先写正常及拒绝用例，再实现注册、登录、老客户绑定三种用途。邮箱验证接口只在用户入口开放，不接受角色或站点参数。公共契约先改 `contracts/operations.json`、`contracts/schemas.mjs` 等源文件，再重新生成，不手改生成物。
- [ ] 注册须在同一数据库事务中消费成功验证码并创建唯一 `CUSTOMER`，提交后签发用户端会话。登录码只能登录既有已验邮箱账号；绑定要求已登录客户验证邮箱并加到原账号。已有归主的邮箱不抢占，不用注册流程登录他人的老账号。
- [ ] 默认随机 6 位、10 分钟有效、60 秒可重发、每次挑战最多 5 次错误。验证码只存带服务端密钥的摘要，绑定用途、目标邮箱及必要的绑定账号；同用途重发使旧码失效，成功后不可重放。按邮箱、可信来源限流，响应不泄露邮箱注册状态；不盲信客户端转发头。发送失败不可凭空通过验证。
- [ ] `web/src/user/` 提供「邮箱注册」「邮箱登录」「手机号登录」及失败、过期、重发状态。验证码和会话不写前端持久存储。注册可不填手机号；创建收货地址仍填联系手机号。记录邮箱自助注册对现有 COD 防重复占位的影响；不得削弱已有下单限额或风控。

## 3. 后台骑手开户

- [ ] 增加开户契约、身份域业务命令和 `web/src/admin/` 表单。首版仅 `SECURITY_ADMIN` 在管理入口经近期 MFA 开户；站点依据服务端授权。创建员工绑定、授予且只授予 `RIDER`、创建骑手资料和记审计须原子提交。不能给运营或财务额外赋权。
- [ ] 仅绑定经授权核对的受信 `issuer/subject`，不按显示名或邮箱自动授权。骑手初始不可接单；管理员确认身份绑定并启用后，仍须通过员工登录与 MFA 才能履约。无可信绑定时保持不可用；不要要求待激活骑手先登录才能启用。配送端无自助注册按钮，服务端无公开骑手开户接口，不发默认密码。
- [ ] 验证停用即时使骑手会话失效、不能继续接新单；在途单按现有运营交接规则处理并留痕，不静默丢单或伪造送达。验证跨站点、普通用户、普通运营、财务以及未通过近期 MFA 的开户请求均被拒。

## 4. 发件地址与通知

- [ ] 在 `backend/cmd/api/`、`backend/internal/bootstrap/` 和部署配置接入服务端发信适配器。仅接一种经批准的邮件 API 或带 TLS 的 SMTP；使用专用发件地址。密钥和验码密钥只通过受控服务器配置注入，缺配置时禁止启用相应能力。不得把测试签发器或验证码旁路带进生产。
- [ ] 新邮箱注册和事务通知分别设开关；写清关闭新注册后老客户邮箱登录/恢复及手机号入口的行为。验证码发送失败可按限流规则再申请，不补发过期码。
- [ ] 事务通知首版只发下单成功、取消、配送异常；收件人为订单所属账号的已验证邮箱。复用持久事件机制，按事件和收件对象去重，有限重试并记录最终失败；邮件失败不得回滚订单。不虚称供应商投递绝对仅一次。邮件不含完整宿舍地址、电话或支付凭据。
- [ ] 本机用合成收件箱测试。获授权后再核实发件域名、真实验证码及通知到达；服务商显示已接受不等同收件箱收到。证据不得包含真实密钥、完整连接串、会话、验证码或个人信息。
